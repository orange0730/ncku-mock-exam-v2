## 大題一 eBNN 推論

### Part A `bnn.c`

| 函式 | 起始檔的錯 | 修正 |
|---|---|---|
| `popcount32` | 迴圈只跑 31 次，第 31 位沒算 | 跑 32 次，或用 SWAR / `__builtin_popcount` |
| `bnn_hidden` | ① XOR 算的是「不同」，要 XNOR `~(a ^ w)`；② `>` 應為 `>=`；③ 神經元放在 `31 - j`，要放在 `j` | 三個都改 |
| `bnn_scores` | `p - 32` 應為 `2p - 32`（相同 +1、不同 −1） | |
| `bnn_infer` | `>=` 讓同分時選到最後一個，規格是最小 index | 改成 `>` |

這幾個錯都會讓程式「看起來在跑」：分數全部一樣、或預測永遠是 9。資料集約有 4.5% 的影像會同分，所以 tie-break 一定會被測到。

### Part B `xnorpop.pio`

- 起始檔把極性弄反了（數的是 1 不是 0），又用 `set x, 31` 當起點。`jmp x--` 只能遞減，要從 `0xFFFFFFFF`（`mov x, ~null`）往下數，最後 `~x` 才等於次數。
- **為什麼「數 0」難優化？** 數 1 時，1-bit 可以 `jmp x-- loop` 直接回圈；就算最後多跑一次 `out`，空的 OSR 移出 0，走 0 的路徑被 `!osre` 擋下，迴圈會結束。數 0 時照抄，多跑的那次 `out` 移出的 0 又被數到，**永遠出不去**。
- 解法：`pull` 之後先 `mov osr, ~osr`，「數 d 的 0」變成「數 ~d 的 1」，再用數 1 的最佳迴圈。

| 寫法 | 指令 | 週期 / word | 效率分 |
|---|---:|---:|---:|
| 修好但沒優化（0-bit 走 4 週期） | 8 | 116 | 4 + 4 = 8 |
| 參考解答（先反相） | 9 | 102.5 | 6 + 4 = **10** |

### Part C `ebnn_node.py`

① 影像型別是 `UInt64` 不是 `UInt32`（型別不同，兩端根本連不上，`ros2 topic info` 會看到兩個型別）；② topic 是 `/ebnn/scores`；③ 低 32 位是 `img[0]`，起始檔把高低位對調了；④ 先發 scores 再發 prediction；⑤ `bnn_lib` 回傳的是 ctypes 陣列，`Int32MultiArray.data` 只收 list / tuple / array，要 `[int(v) for v in scores]`。

## 大題二 兩片板子平行推論

### Part A `firmware.c`

| 起始檔 | 錯在哪 |
|---|---|
| 沒檢查 `n` | `n != 3` 時讀出界 |
| `first = (h >> 8) & 0x0F` | first 是 8 位元欄位，16..31 會變成 0..15 |
| 沒檢查範圍 | `count == 0`、`count > 32`、`first + count > 32` 都要回傳 -1 |
| `img = { req[2], req[1] }` | 高低位對調 |
| `(1u << count) - 1` | `count == 32` 時是 UB（ARM / x86 實際上都得到 0） |
| 重組 header | 規格是「原樣送回」；重組會把錯的 first 也送回去，協調者對不上帳 |

### Part B / C `coordinator.py`

起始檔的錯：header 欄位位置錯、一次只送一張、固定對半切、用回應到達的順序發布。

參考解答的排程（自己記帳：每片板子預計什麼時候有空）：

- **兩片都閒著** → 依速度把 32 個神經元切開（找讓兩邊同時做完的切點，約 21 / 11）→ 單張延遲最低。
- **有積壓** → 整張影像給「最早能做完它」的那片 → 每張只付一次 request 固定成本，吞吐量最高。

各種策略的實測（模擬時間，結果是確定的）：

| 策略 | 吞吐量加速比 | 平均延遲 | Part C 分數 |
|---|---:|---:|---:|
| 只用 board0 | 1.00 | 36 ms | （工作分配不及格） |
| 對半切 + pipeline | 1.00 | 36 ms | 0 + 3 |
| 永遠依速度切 + pipeline | 1.45 | 26 ms | 11 + 10 |
| 永遠整張分派（依速度加權） | 1.48 | 36 ms | 11 + 3 |
| **自適應（參考解答）** | **1.50** | **26 ms** | **15 + 10** |

重點觀念：**模型平行降低延遲，資料平行提高吞吐量**；快慢不同的機器要依速度分配；送出去就別等，讓佇列裡一直有工作；用序號對帳、依序發布。

## 大題三 排序 / SHA-0 / CRC-32

### Part A `algos.c`

| 函式 | 起始檔的錯 | 參考解答 |
|---|---|---|
| `sort_u32` | `i < n - 1` 漏掉最後一個；`n == 0` 時 `n - 1` 變成 `SIZE_MAX`，讀出界當掉；O(n²) | LSD radix sort（4 輪 × 8 位元），在 Pi 5 上 100 萬筆約 15 ms，qsort 約 135 ms |
| `sha0` | ① 訊息排程多了 `rotl(…, 1)`（那是 SHA-1）；② 40–59 輪要 majority 不是 parity；③ 長度要 big-endian；④ 剩餘 ≥ 56 bytes 要多補一個區塊 | 四個都改 |
| `crc32_sw` | ① 反射版要用 `0xEDB88320`；② init 與 xorout 都是 `0xFFFFFFFF`；③ 逐位元太慢 | 256 項查表，在 Pi 5 上約快 3.6 倍（slicing-by-8 可以更快） |
| `crc32_dma` | ① count 填 bytes 又用 `XFER_32`：搬 4 倍、位址不對齊就中止；② 標準 CRC 是反射的；③ `len == 0` 引擎不接受；④ 沒有 disable sniffer 就 release（引擎會中止）；⑤ 沒檢查 claim 失敗 | `XFER_8`、`dst_increment = false`；`SNIFF_CRC32_REV` + 初值 `0xFFFFFFFF` + 讀出時反轉並反相 |

### Part B / C `dispatcher.py`

起始檔的錯：job id 用 big-endian 解；CRC 在 dispatcher 用 `zlib` 自己算（違反分工）；一次一個工作，而且排序做完才送 SHA-0；median 取 `n // 2 - 1`；crc 用大寫、沒補零；pipeline 後沒有依序發布。

| 策略 | 加速比 | Part C |
|---|---:|---:|
| 三個依序做（起始檔的想法） | ≈ 1.0 | 0 |
| 三片同時做，但一次一個工作 | 2.36 | 10 |
| **三片同時做 + pipeline（參考解答）** | **2.75** | **15** |

上限由最慢的那片板子決定（board_sort 約 11 ms / 工作）。三個演算法輪流做是 31 ms，所以理論上限約 2.8 倍。
